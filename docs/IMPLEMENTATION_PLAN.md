# Real-Time Room Chat — Implementation Plan

End-to-end plan for building a real-time chat app with rooms, a display-name
entry page, live messages with timestamps, a professional UI, and public access
through GitHub Codespaces.

Repository: <https://github.com/logeshps02/chat_room_project>

---

## How to use this plan

Each step has five sections:

1. **What we will do**: the concrete work.
2. **What must be achieved**: the acceptance criteria.
3. **What to test**: manual and automated checks.
4. **Done when**: the exit gate.
5. **Git push**: the exact commit to push once the tests pass.

Do not start a step until the previous step is pushed and its tests pass.

### Standard commit-and-push routine (used by every step)

```bash
git checkout main
git pull origin main
# ... do the work for the step ...
git status --short                 # review what changed
git diff                           # review content
git add <explicit files for this step>
git diff --cached                  # confirm only intended files are staged
git commit -m "<step commit message>"
git push origin main
```

Rules:

- Never commit `.env`, database files (`*.db`, `*.db-wal`, `*.db-shm`),
  `node_modules/`, `dist/`, or logs.
- Run the step's tests **before** committing.
- After pushing, check that the GitHub Actions run passes (from Step 9 onward).
- For team work, use a branch per step (`git checkout -b step-NN-name`), open a
  pull request, and merge only after CI passes.

## 0. Scope, constraints, and architecture

### Hosting limitations (read first)

GitHub Codespaces can expose the app publicly, but **it is not an always-on
production host**:

| Limitation | Detail |
|---|---|
| Public access | A port set to **Public** is reachable by anyone with the URL, with no GitHub login required |
| Idle timeout | Default 30 minutes; configurable from 5 to 240 minutes in personal settings (organization policies may lower it) |
| Maximum lifetime | 12 hours per run, even while active, after which it must be restarted |
| Cost | Compute hours and storage use your free quota, then are billed |
| URL | `https://<codespace-name>-3000.app.github.dev`; it changes if you create a new codespace |
| Data | Deleting the codespace deletes its local database |

So this plan delivers a **publicly reachable MVP while the codespace is
running**. For 24/7 availability, deploy the same app to a persistent host later.

References:
[Port forwarding](https://docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace) ·
[Timeouts](https://docs.github.com/en/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces) ·
[Lifecycle](https://docs.github.com/en/codespaces/about-codespaces/understanding-the-codespace-lifecycle) ·
[Billing](https://docs.github.com/en/billing/concepts/product-billing/github-codespaces)

### MVP features

| Area | Behavior |
|---|---|
| Display name | Required, trimmed, 2–30 characters |
| Room name | Required, 2–40 characters, letters/digits/space/`-`/`_`; normalized (trimmed, lowercased) |
| Room creation | The first join creates the room |
| Messages | Plain text, 1–2,000 characters |
| Timestamps | Generated by the server in UTC and shown in each viewer's local time |
| History | Latest 50 messages on join; older messages loaded by cursor |
| Presence | Participant list and online count per room |
| Connection state | Connected / reconnecting / offline indicator |
| Send state | Pending → sent, or failed with a retry option |
| Layout | Responsive for desktop and mobile; keyboard accessible |
| Persistence | SQLite |

**Identity caveat:** a display name is guest identification, not
authentication. Names can be duplicated or impersonated. Rooms are public to
anyone who knows the name. The UI should say "Enter chat", not "Log in
securely".

### Tech stack

- **Frontend:** React + TypeScript + Vite + Tailwind CSS
- **Backend:** Node.js (current LTS) + Express + TypeScript
- **Real-time:** Socket.IO
- **Validation:** Zod schemas shared between the client and server
- **Database:** SQLite (`better-sqlite3`) with versioned migrations
- **Tests:** Vitest, React Testing Library, `socket.io-client` integration
  tests, Playwright end-to-end tests
- **CI:** GitHub Actions
- **Runtime:** one Node process on port `3000`, serving both the API and the
  built frontend (single origin, no CORS complexity)

### Data model

```text
rooms(
  id INTEGER PK,
  name TEXT UNIQUE NOT NULL,       -- normalized
  display_name TEXT NOT NULL,
  created_at TEXT NOT NULL         -- ISO UTC
)

messages(
  id INTEGER PK AUTOINCREMENT,     -- also used as the ordering cursor
  room_id INTEGER NOT NULL REFERENCES rooms(id),
  sender_id TEXT NOT NULL,         -- guest participant id
  sender_name TEXT NOT NULL,       -- snapshot at send time
  body TEXT NOT NULL,
  client_msg_id TEXT NOT NULL,     -- for retry deduplication
  created_at TEXT NOT NULL,        -- server UTC ISO string
  UNIQUE(sender_id, client_msg_id)
)
INDEX messages(room_id, id)
```

Guest sessions are signed HttpOnly cookies containing
`{ participantId, displayName, expiresAt }`. A server-side table is optional.

### Real-time contract

| Direction | Event | Payload | Ack |
|---|---|---|---|
| C→S | `room:join` | `{ room, afterId? }` | `{ ok, data: { room, history, participants } }` |
| C→S | `room:leave` | `{}` | `{ ok }` |
| C→S | `message:send` | `{ text, clientMsgId }` | `{ ok, data: message }` |
| C→S | `history:before` | `{ beforeId, limit }` | `{ ok, data: messages[] }` |
| S→C | `message:new` | `message` | — |
| S→C | `room:presence` | `{ participants, count }` | — |

Error shape: `{ ok: false, error: { code, message } }`, where `code` is one of
`VALIDATION`, `NOT_IN_ROOM`, `RATE_LIMITED`, `UNAUTHENTICATED`, or `INTERNAL`.

### Reliability rules

- The sender's identity comes from the session, **never** from the payload.
- Persist the message, then acknowledge it, then broadcast it to that room only.
- Each socket has one active room. Switching rooms leaves the previous one first.
- Retries with the same `clientMsgId` return the existing message, not a duplicate.
- On reconnect, rejoin automatically and fetch messages newer than the last
  received ID.
- Presence counts unique participants, not sockets, so multiple tabs count once.

## Step 4: Rooms (join, leave, switch) and presence

### What we will do

1. **Database:** create the migration runner and the `rooms` table, plus
   `npm run db:migrate`.
2. **Socket authentication:** in the Socket.IO middleware, read the session
   cookie from the handshake. Reject connections without a valid session using
   `UNAUTHENTICATED`. Attach `participantId` and `displayName` to
   `socket.data`.
3. **`room:join`**
   - Validate the name and normalize it with `trim().toLowerCase()`.
   - Upsert the room in a transaction.
   - Leave the socket's current room, if any.
   - Call `socket.join("room:<id>")` and record membership in an in-memory
     presence map: `roomId → participantId → Set<socketId>`.
   - Acknowledge with room information and participants. History arrives in
     Step 6.
   - Broadcast `room:presence` to that room.
4. Implement **`room:leave`** and **disconnect** to remove the socket from
   presence and broadcast updated presence when the participant has no
   remaining sockets.
5. **Client**
   - Create a `JoinRoom` page with a room-name input, inline validation, and
     an optional "recent rooms" list from `localStorage`.
   - Create a `ChatRoom` layout with a header (room name, online count,
     **Leave** button) and a participant sidebar or drawer.
   - Add a connection-status badge for connected, reconnecting, and offline
     states.

### What must be achieved

- Users with the same normalized room name are in the same room.
- Presence is accurate when users join, leave, switch rooms, close tabs, or
  use multiple tabs.
- Unauthenticated sockets cannot do anything.

## Step 5: Live messaging with timestamps

### What we will do

1. **Database:** add a migration for the `messages` table, unique constraint,
   and index.
2. **`message:send`**
   - Check that the socket is in a room; otherwise return `NOT_IN_ROOM`.
   - Validate `text`, trim it, and require 1–2,000 characters. Validate
     `clientMsgId` as a UUID.
   - Set `created_at = new Date().toISOString()` on the server and ignore any
     client time.
   - Insert the message. On a unique-constraint conflict, return the existing
     row.
   - Acknowledge with the saved message.
   - Emit `message:new` to `room:<id>` only.
3. **Client**
   - Build a `MessageList` showing the avatar (initials with a color derived
     from `participantId`), sender name, text, and time (`h:mm a`, with the
     full date in the tooltip).
   - Add date separators such as "Today", "Yesterday", and `Nov 11, 2026`.
   - Group consecutive messages from the same sender within five minutes.
   - Visually distinguish the user's own messages.
   - Build a `Composer` textarea. Enter sends and Shift+Enter adds a new line.
     Do not send during IME composition. Disable Send for empty input and show
     a character counter near the limit.
   - Use optimistic sending: show the message as **pending**. Replace it with
     the acknowledged message, matched by `clientMsgId`. After a 10-second
     timeout or error, mark it **failed** with a **Retry** button that reuses
     the same `clientMsgId`.
   - Deduplicate incoming `message:new` events by `id` and `clientMsgId`.
   - Remove socket listeners on unmount or room change.

### What must be achieved

- Messages appear instantly for everyone in the same room and nobody else.
- Every message has a server timestamp shown in local time.
- The sender sees a clear pending, sent, or failed state.

## Step 8: Security hardening for public access

### What we will do

1. **XSS:** render messages only as React text (no
   `dangerouslySetInnerHTML`). Optionally auto-link URLs with
   `rel="noopener noreferrer"` after safe escaping.
2. **Validation:** use Zod on every REST body and socket payload. Reject
   unknown fields.
3. **Rate limits**
   - `POST /api/session`: 10 per minute per IP
   - `room:join`: 20 per minute per participant
   - `message:send`: 5 per 5 seconds burst, 60 per minute per participant
   - Socket connections: 20 per minute per IP
   - Rate-limited requests return `RATE_LIMITED`.
4. **Payload limits:** `express.json({ limit: "10kb" })` and Socket.IO
   `maxHttpBufferSize: 16_000`.
5. **Headers:** use `helmet` with a CSP that allows `self` and `wss:` for the
   public URL.
6. **Origin checks:** set the Socket.IO `cors.origin` and an Express check to
   `ALLOWED_ORIGIN`, which is the Codespaces public URL.
7. **Secrets:** read `SESSION_SECRET` from the environment or a Codespaces
   secret. Refuse to start in production if it is missing.
8. **Logging:** log events and errors, but never message bodies or cookies.
   Return generic errors without stack traces.

### What must be achieved

Public exposure does not enable easy script injection, spam floods, crashes
from bad input, or impersonation.

### What to test

| # | Test | Type | Expected |
|---|---|---|---|
| 8.1 | Send `<img src=x onerror=alert(1)>` | Manual and E2E | Shown as literal text; no alert |
| 8.2 | Send 20 messages in 1 second | Integration | Later messages receive `RATE_LIMITED`; server remains healthy |
| 8.3 | Send a 1 MB socket payload | Integration | Rejected or connection dropped; server unaffected |
| 8.4 | Send malformed JSON or unknown fields | Integration | `400` or `VALIDATION`; no crash |

## Step 10: Codespaces configuration and public hosting

### What we will do

1. Add `.devcontainer/devcontainer.json`:

   ```json
   {
     "name": "chat-room",

     "forwardPorts": [3000],
     "portsAttributes": {
       "3000": { "label": "Chat App", "onAutoForward": "notify" }
     },
     "postCreateCommand": "npm ci && npm run build && npm run db:migrate",
     "secrets": {
       "SESSION_SECRET": { "description": "Random string used to sign session cookies" }
     }
   }
   ```

   Use the same Node.js LTS version as CI.

2. In GitHub **Settings → Codespaces → Secrets**, create `SESSION_SECRET` and
   grant access to this repository.
3. Rebuild or create the codespace, then run:

   ```bash
   export ALLOWED_ORIGIN="https://${CODESPACE_NAME}-3000.${GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN}"
   NODE_ENV=production npm start
   ```

   The server must bind to `0.0.0.0:3000`.

4. Open the **Ports** tab, right-click port `3000`, and choose
   **Port Visibility → Public**. If the option is unavailable, an organization
   policy blocks it; use a personal-account repository or ask an admin.
5. Copy the URL, `https://<codespace-name>-3000.app.github.dev`.
6. Optionally make visibility automatic with
   `gh codespace ports visibility 3000:public -c $CODESPACE_NAME` in a
   `postStartCommand` or helper script.
7. Add `scripts/start-public.sh`, which sets `ALLOWED_ORIGIN`, starts the app,
   and makes the port public.

## Final definition of done

- [ ] A signed-out visitor opens the public URL and sees the display-name page.
- [ ] They enter a name, join a room by name, and see participants.
- [ ] Messages appear live for everyone in that room only.
- [ ] Every message shows a server-generated timestamp in local time.
- [ ] History survives refresh and server restart.
- [ ] Reconnects and retries do not lose or duplicate messages in tests.
- [ ] The UI is professional, responsive, and keyboard accessible.
- [ ] Inputs are validated and rate limited, and HTML is not executed.
- [ ] CI is green, and each step is committed and pushed to GitHub.
- [ ] Hosting limitations are documented, and `v0.1.0` is tagged.
